- (direction) Triggered bmad-party-mode pour inviter architecte, UX, dev, PM avec des réponses directes et concises
- (direction by user) Nouvel apport : l'identifiant unique d'une application = nom du repo distant ; paramétrage pour initialiser un espace dans le HUB pointant vers le repo distant ; alimentation temps réel (toutes les 10s, paramétrable) d'un dashboard d'état du projet et des artifacts BMAD
- (idea by user) Substitute: le Client Python communique automatiquement le nom du repo distant auquel il est connecté au lancement -> rejoint automatiquement le bon espace HUB -> le dashboard affiche automatiquement le membre, zéro configuration manuelle côté user
- (idea by coach) Combine: pas d'étape manuelle 'créer un espace' côté HUB — le 1er client à annoncer un nom de repo inconnu crée l'espace à la volée, les suivants avec le même nom le rejoignent automatiquement (auto-clustering par identifiant repo)
- (idea by user) Résolution collision: utiliser le chemin complet du remote (org/repo, voire host inclus) comme identifiant unique réel, pas juste le nom court du repo
- (idea by coach) Two-tier naming: ID technique = chemin complet (host/org/repo), nom affiché dashboard = nom court du repo ; badge/tooltip org visible seulement en cas d'ambiguïté entre 2 espaces au même nom court
- (idea by user) Modify: init automatique SI le HUB a déjà l'accès lecture au repo distant ; sinon message d'alerte envoyé au dev pour l'informer que le HUB doit obtenir la permission d'accès
- (idea by coach) Le message d'alerte embarque un lien direct d'action (deploy key / install app selon provider détecté) pour résoudre en 1 clic ; en attendant, l'espace existe déjà côté HUB avec statut '🟡 En attente d'accès' plutôt que de ne pas exister
- (direction by user) Invoque bmad-party-mode pour recueillir des propositions multi-perspectives sur le mécanisme d'auto-join/auto-init HUB via identifiant repo distant
- (idea by coach) Party-mode (archi/UX/dev/PM) converge sur: ID technique=chemin complet host/org/repo avec contrainte d'unicité en base; nom affiché=nom court; statut d'accès 3 valeurs (pending/active/access_revoked) au lieu d'un booléen; lien d'action scoped au provider unique du projet + fallback texte générique (pas de détection multi-provider en MVP)
- (decision by user) Zéro-config au premier lancement (auto-join via nom repo) est un choix de design assumé, pas un besoin utilisateur observé -> rester minimal viable tant que non validé sur le terrain
- (idea by user) Le Client Python doit aussi remonter l'état du repo local: déphasage/décalage (ahead/behind), action en cours (rebase/merge/conflit)
- (idea by coach) Party-mode converge: état repo local piggyback sur heartbeat WebSocket AD-002 existant, envoi immédiat via hook Git local + tick 10s en filet de sécurité; donnée brute alimente à la fois FR5 (carte contributeur enrichie) et FR10/Epic4 (signaux de risque agrégés) - une seule source, deux consommateurs. Validé par l'utilisateur.

Directions retenues: ID technique=chemin complet host/org/repo, nom affiché=court, statut d'accès 3 valeurs, auto-clustering à la volée côté HUB, état repo local piggyback sur heartbeat AD-002 alimentant FR5+FR10/Epic4.
