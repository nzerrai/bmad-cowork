## Story

As a Tech Lead / Analyst,
I want to see the traceability matrix showing the link Idée/Brief -> PRD -> Archi/UX -> Stories -> PRs -> Tests,
so that I can verify complete coverage and requirement fulfillment.

**FR3** — see FR Coverage Map in `epics.md`. Governed by `ARCHITECTURE-SPINE.md` AD-006 (MVP Data Layer — same plain relational/JSONB store as Stories 1.1/1.2, no new persistence model). Third and final story of Epic 1 (Sprint 1); reads Story 1.1's `artifacts`/`artifact_links` tables and reuses Story 1.2's per-type completeness pattern. Depends on Story 0.2's auth/RBAC substrate for its endpoint, same as Story 1.2.

## Acceptance Criteria

1. **Given** artifacts and stories are indexed (Story 1.1's `artifacts` table), **when** the user views the traceability matrix, **then** the linear or graphical view shows the complete lineage from idea to tests — Idea/Brief -> PRD -> Architecture -> UX -> Story -> PRs -> Tests — for every Epic/Story pair defined in the project's roadmap (`epics.md`), not only the ones that already have a story file on disk.
2. **And** each node in the matrix shows its status: `completed` (the Story node's own workflow lifecycle reached `done`), `pending` (the node's artifact exists but is unfinished/malformed), or `linked` (the node's artifact exists and is healthy) — exact per-node-type rule in Dev Notes/Task 2, since AC text alone doesn't define which of the three applies to which node kind.
3. **And** a node with no artifact yet (e.g. a Story with no linked PR) shows as `not_started` rather than being omitted from the matrix — this is the expected, common case for the PRs and Tests columns in this MVP (see Dev Notes: no Git/PR integration and no Tests-artifact convention exist yet), not just a rare edge case.

## Dev Notes

- **FR3 is the thinnest-sourced FR in Epic 1.** The 2026-08-06 Implementation Readiness report marks it 🔶 ("le PRD mentionne 'Traceability matrix' pour le rôle Architect (§2) mais sans détailler la chaîne complète") — there is no §3.x PRD section, no dedicated mockup, and (confirmed by direct inspection) no "Traceability Matrix" row anywhere in `EXPERIENCE.md`'s Information Architecture table. The concrete node-status rules and node set adopted in Task 2 are this story's scope decision, exactly like Story 1.2's completeness/sync-status rules were — flag them for the reviewer, don't assume pre-agreement.
- **The real data graph today is much sparser than FR3's chain implies — this is the single most important thing to understand before writing code.** Verified directly against the live `prjdocs/` tree: `brief.md` and `prd.md` have **no** cross-reference frontmatter keys of their own (neither references the other); only `epics.md` (`inputDocuments`) and the Architecture spine (`sources`/`companions`) carry real `artifact_links` edges, and Story-type files carry **zero** frontmatter, hence zero outbound links, ever (Story 1.1 Dev Notes, confirmed unchanged). A traceability matrix built by chasing `artifact_links` edges the way Story 1.2's dashboard does would render almost every node "unlinked" and be useless. That's why this story does **not** reuse Story 1.2's edge-following approach for the matrix — it instead treats `idea_brief`/`prd`/`architecture`/`ux` as **existence/health checks per type** (reusing the exact same signal Story 1.2's completeness rollup already computes) and derives the **Story** axis structurally from `epics.md`'s own document headings (Task 2), not from any `artifact_links` row. This is a deliberate, disclosed design choice, not a misunderstanding of AD-006's edge model — the edge model still exists and still backs Story 1.2's dashboard; this story simply doesn't have enough real edges to build a meaningful matrix from it alone.
- **The PRs and Tests columns are `not_started` for every single row in this MVP, unconditionally, and that is correct.** Epic 2 (Git/remote integration, AD-005/AD-008) and Epic 3 (claims) — the only stories that would ever produce real PR data — are both still `backlog`. `ArtifactType.TESTS` has had zero real file-naming convention since Story 1.1 shipped ("no QA test-design docs, no standalone decision files... zero matches is correct behavior, not a bug"). AC3's own example — "e.g. a Story with no linked PR" — already anticipates this being the common case, not a rare edge. Don't build speculative Git-PR-lookup logic here; that infrastructure doesn't exist yet and building against it would repeat the exact "don't build against unbuilt infra" mistake Story 1.1's Dev Notes explicitly warned against for Epic 2/3.
- **Why `completed` only ever applies to the Story node.** AC2 lists three status words (`completed`/`pending`/`linked`) without saying which node gets which. Document nodes (Brief/PRD/Architecture/UX) don't have a workflow lifecycle — a PRD is never "completed," it either exists and is healthy (`linked`) or it doesn't (`not_started`) or it's malformed (`pending`). Only the Story node represents actual tracked work with a real done/not-done lifecycle, which is exactly why Task 1 resolves the previously-deferred Story-status body parsing now — without it, `completed` would have no real signal to key off anywhere in the matrix and the AC's own vocabulary would go unused for its one legitimate case.
- **`sprint-status.yaml` is deliberately not read by this story.** It has the full epic/story roadmap and per-story lifecycle status already, and reading it would arguably be *less* work than parsing `epics.md`'s headings. It's rejected anyway: it isn't one of FR1's 11 catalogued artifact types, isn't indexed by Story 1.1's engine, and isn't governed by AD-006/AD-008's "one canonical read model per data source" discipline the way `epics.md` and the `artifacts` table are. Introducing it here would create a second, ungoverned roadmap source that could silently drift from `epics.md` (e.g. a story renamed in one but not the other) with nothing to catch it. `epics.md` is already indexed, already the project's own source of truth for epic/story structure, and reusing it keeps this story inside the existing artifact-index architecture instead of reaching outside it.
- **Reuse, don't duplicate:** the per-type `missing`/`incomplete`/`complete` rollup must be extracted from `health.py` into a shared pure function (Task 2) and called from both `compute_health` and `compute_traceability` — a second, slightly-different copy of that loop would be exactly the kind of drift risk Story 1.2 avoided by promoting `hash_content` to a public function.
- **NFR1** (100% deterministic, zero LLM calls) applies directly: heading-regex extraction, DB queries, and status remapping are all deterministic, no LLM involved anywhere in this story.
- **Known gap, not silently handled:** an indexed Story artifact whose filename's `(epic, story)` numeric prefix doesn't match any heading pair actually present in the current `epics.md` (e.g. a renamed/renumbered story, or a stale file) simply won't appear in the matrix — there's no reconciliation/orphan-detection in this story's scope. Flag this for the reviewer as a candidate `deferred-work.md` entry if it isn't addressed here, same pattern as Story 1.1/1.2's own deferred items.

- **`health.py`'s per-type rollup loop extracted into `type_completeness_rollup`** (pure function, takes `list[Artifact]`), called from both `compute_health` and the new `traceability.compute_traceability` — one shared "is this type present/error-free" signal, not two copies.
- **`traceability.py` derives the Story axis from `epics.md`'s own headings**, not from `ArtifactLink` edges — the real data graph is too sparse for edge-following to produce a useful matrix (see the story's own Dev Notes). Epic attribution: each `### Story N.M` heading is attributed to whichever `## Epic N: Title` heading precedes it in document order (position-sorted merge of both header streams), not from the Story heading's own leading number — matches the story's literal instruction and is robust to the (currently nonexistent) case of the two disagreeing.
- **Document nodes (`idea_brief`/`prd`/`architecture`/`ux`) carry `artifact_id`/`title`/`file_path` as `null`** on every row — they're a type-level completeness signal (same value repeated across all rows), not a reference to one specific artifact, so there's no single instance identity to populate those fields with.
- **Verified against the real `prjdocs/` tree** (see Debug Log): 32 real roadmap rows (Epics 0–7), correct sort order, correct CORS header, Story 1.3's own row self-reporting `pending` (expected — its own `Status:` line isn't `done` yet).
- **Test-infra fix required by this story, not pre-existing:** `next/link`'s prefetch-on-idle effect calls `self.setTimeout(...)` unconditionally in its non-native fallback; jsdom never aliases `self` to `window` the way real browsers do. This is the first story to use `next/link` anywhere in the IHM (both the new page and the `/artifacts` cross-link), so it's the first time this surfaced — it broke the *existing* `artifacts.test.tsx` too, not just the new test. Fixed by aliasing `globalThis.self = dom.window` in `__tests__/jsdom-register.mjs`.
- **Known gap, flagged per the story's own Dev Notes:** no reconciliation/orphan-detection for an indexed Story artifact whose filename prefix doesn't match any `epics.md` heading pair (e.g. a renamed/renumbered story) — it simply won't appear in the matrix. Not built in this story's scope; flagging for the reviewer as a candidate `deferred-work.md` entry per this project's established provenance convention (entries are logged from code-review findings, not proactively during dev).
- **IA gap carried forward from Story 1.2, same call:** `/artifacts/traceability` is nested under `/artifacts` rather than a new top-level route, since `EXPERIENCE.md`'s Information Architecture table still has no dedicated row for either Epic-1 catalog surface. Flagging again per Story 1.2's precedent, not assuming it's resolved.
