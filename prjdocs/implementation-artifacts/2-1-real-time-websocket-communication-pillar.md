# Story 2.1: Real-time WebSocket Communication Pillar

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Developer,
I want a persistent real-time WebSocket connection between my Client/IHM and the Backend,
so that presence, notifications, and command dispatch happen instantly without polling.

**FR5** ("WebSocket Pillar — The Nervous System") — see FR Coverage Map in `epics.md`. First story of Epic 2 (Sprint 2); nothing in Epic 2 exists yet (`epic-2: backlog` before this story, all five of its stories `backlog`). Governed by `ARCHITECTURE-SPINE.md` AD-002 (heartbeat mechanism), AD-005 (Client-side Git Authority — this story never lets the Backend touch local disk), and AD-008 (this story only builds the *transport*; the one-canonical-record state-reporting model AD-008 describes is Story 2.5's job). This is this project's second **enabler** story (after Story 1.1): FR5 explicitly names presence/notifications/command-dispatch/state-reporting as consumers, but every one of those concrete features (Zero-Setup Onboarding presence — 2.3; Local Repo State Reporting — 2.5; Lease/Claim heartbeat — 3.1; Auto-Healing Sync — 3.2; Real-time Status Bar — 3.3; instant notifications — FR23/Epic 3) is still `backlog`. This story builds the connection, auth, heartbeat, reconnect, and message-envelope substrate those stories will attach real payloads to — it does not itself implement leases, spaces, or notifications.

## Acceptance Criteria

1. **Given** a Client or IHM connects to the Backend, **when** a presence, notification, or command event occurs, **then** it is delivered over the WebSocket connection in real time. *(Scope for this story: "presence" is the one concrete event type built here — a connect/disconnect broadcast, proven by two simultaneous connections in Task 2's tests. "Notification" and "command dispatch" have no concrete payload yet in this MVP slice — Epic 3 defines them — so AC1 is satisfied for those by the envelope being generic/extensible (Dev Notes), not by a working notification/command feature that doesn't exist yet.)*
2. **And** the Backend acts as the bridge/final arbiter for claims and state changes routed to the remote repository. *(No claim/state-change logic exists yet — Epic 3. Satisfied here by topology only: every Client/IHM connects to the Backend, never to each other directly or to the remote repo via any path this story builds — see Dev Notes/Task 1.)*
3. **And** if the WebSocket connection drops, the Client/IHM automatically attempts reconnection with backoff, and the Real-time Status Bar (Story 3.3) reflects the disconnected state until it recovers. *(Story 3.3's actual Status Bar UI doesn't exist yet — this story's job is the reconnect-with-backoff behavior itself, on both Client and IHM, plus an observable connection-state signal 3.3 will consume later. No UI is built here — see Dev Notes' "no premature UI" scope note, same discipline Story 1.1 applied to its own enabler role.)*

## Dev Notes

- **This is an enabler story, structurally like Story 1.1 — read its framing note before writing code.** FR5 names four consumers (presence, notifications, command dispatch, state reporting) and AD-002/AD-008/AD-009 name three more concerns (lease heartbeat, state-reporting canonical record, two-axis status). *None* of those consuming features exist yet — every other Epic 2 story and all of Epic 3 are still `backlog` at the time this story is written. Resist the temptation to half-build any of them here (no lease table, no space/contributor model, no notification UI). This story's job is exactly: authenticated persistent connections, a heartbeat channel, reconnect-with-backoff on both non-Backend tiers, and a minimal, generically-typed message envelope those later stories attach real payloads to.
- **Why presence-broadcast-on-connect/disconnect is the concrete AC1 proof, not something invented beyond scope.** AC1 requires *something* to be "delivered over the WebSocket connection in real time" to be verifiable at all — an empty pipe proves nothing. Presence is the one FR5-named concept buildable today without any of the not-yet-built infra (spaces, leases, notifications) — it needs nothing but "who is currently connected," which the `ConnectionManager` registry already tracks for its own purposes. This is deliberately unscoped by "space" (every connected user sees every other connected user's presence, globally) because "Space" (a Hub per remote-repo identity) doesn't exist until Story 2.3 — do not attempt to scope broadcasts by space here; that's explicitly Story 2.3/3.x's job once spaces exist, flag it as a known forward-looking gap in the same way Story 1.3 flagged its own known gaps rather than quietly building against an entity that doesn't exist.
- **Why AC1's "notification" and "command dispatch" aren't built as features here.** There is no notification content (FR23 is Epic 3) and no command semantics (the only named command anywhere in the spec is `[Re-sync]`, FR16, also Epic 3). Building either now would be inventing requirements. AC1 is satisfied for these by the envelope itself: the mandatory `"type"` discriminator field and the "unknown types are ignored, not rejected" rule (Task 1) are exactly what let Epic 3 add `{"type": "notification", ...}` or `{"type": "command", ...}` later without touching this story's connection/auth/heartbeat plumbing.
- **AC2's "final arbiter" is satisfied by topology, not new logic.** Nothing in this story reads from or writes to the remote Git repository, and nothing lets a Client or IHM connect to another Client/IHM directly — every connection terminates at the Backend (`app/realtime/router.py`'s single `/ws` route). That topological fact — reinforced by AD-005 (only the Client ever touches local disk/Git; the Backend never does) — is what AC2 is actually asking this story to guarantee at this stage; the Backend actually *acting* as an arbiter of claims/state changes is Epic 3's job.
- **Query-param token auth, not a header, and why.** The browser `WebSocket` constructor cannot set arbitrary request headers (no `Authorization` header option) — this is a hard platform constraint, not a design preference, so `?token=<jwt>` is the only viable option for the IHM side. The Python Client *could* send a header instead (the `websockets` library supports `extra_headers`), but using the same query-param convention for both tiers keeps the Backend's single `/ws` route's auth logic uniform rather than branching on caller type — do this consistently even though the Client didn't strictly need it.
- **The Origin check is new territory for this codebase — no prior WS/browser-origin precedent exists.** `CORSMiddleware` (Story 1.2) only ever governed plain `fetch`/XHR requests; this is the first time this codebase has had to reason about WebSocket-handshake-level origin validation at all. Keep the check exactly as scoped in Task 1 (compare against the same `IHM_ORIGIN` already used for CORS; allow through when no `Origin` header is present at all) — don't invent a broader allow-list mechanism this story has no requirement for.
- **NFR1** (100% deterministic, zero LLM calls) applies directly and trivially — nothing in this story's connection/auth/heartbeat/reconnect logic involves an LLM call anywhere.
- **NFR6** ("Latence de sync minimale entre un événement Git et sa représentation visuelle dans le Dashboard") is the reason this pillar exists at all — push over a persistent socket instead of polling. This story doesn't yet carry any Git-event payload (that's Story 2.5), but the low-latency channel it establishes is the prerequisite NFR6 depends on.
- **No Alembic migration in this story.** Confirmed above: the connection registry is in-memory only; nothing here is persisted. The first Epic-2/3 story that needs a durable table (a `spaces` table for Story 2.3, most likely) is where the next migration lands.
